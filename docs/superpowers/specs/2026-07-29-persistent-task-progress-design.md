# 统一持久任务、阶段进度与刷新恢复设计

## 背景

当前长耗时操作使用了三种不同的执行方式：

- 专辑大纲与思维导图在一次 HTTP 请求中同步等待完整流程；
- 逐章拆书虽然写入父子运行记录，但仍由请求协程等待整批完成；
- 单条声音与批量终稿已经转为后台任务，但前端轮询依赖当前页面的 React 内存状态。

因此用户点击生成后只能看到按钮处于等待状态，不知道模型正在处理哪个阶段，也无法查看已经完成的阶段结果。页面刷新会丢失选中的书籍、项目、批次和轮询状态；专辑大纲与拆书请求还可能因连接断开而停止。后端启动恢复目前只覆盖声音批次和部分单条声音任务。

## 已确认目标

1. 所有长耗时模型流程使用统一的持久任务生命周期。
2. 点击生成后立即得到任务记录，不让浏览器长时间持有模型请求。
3. 显示阶段级进度、当前阶段、已完成数量、开始时间与耗时。
4. 每次模型调用完成后立即保存并展示该阶段的完整输出。
5. 刷新页面后自动重新发现活动任务并恢复进度展示。
6. 后端进程重启后从最后一个已完成阶段继续。
7. 已完成阶段不重复调用模型；失败阶段支持重跑。
8. 保持现有单条失败隔离、最多五条声音并行和模型/提示词快照规则。

## 非目标

- 不做逐字或逐 token 流式输出。
- 不引入 Redis、Celery、外部消息队列或云端基础设施。
- 不保证关闭本地后端进程期间任务继续运行；后端再次启动后恢复。
- 不允许刷新或重启后使用新修改的模型、提示词或项目输入替换旧任务快照。
- 不在本轮重做知识资产、专辑大纲或声音稿的数据结构。

## 方案比较

### 方案一：仅恢复前端轮询

把当前页面和选中项目写入浏览器存储，并让运行记录页定时刷新。改动较小，但请求协程仍可能随刷新中断，无法保证拆书和专辑大纲继续执行。

### 方案二：统一持久任务与短轮询

所有长任务先写入 SQLite，再由后端进程内执行器运行。前端独立于当前页面每秒读取活动任务。阶段状态和结果保存在现有业务表与任务元数据中，重启时按任务类型恢复。

### 方案三：持久任务与 SSE 推送

后端任务边界与方案二相同，前端通过 Server-Sent Events 接收阶段变化。仍需保留查询接口完成断线补偿和重启恢复，首版本地产品增加了额外连接管理但没有带来逐字流式输出。

采用方案二。

## 核心状态模型

`workflow_runs` 继续作为统一任务表，并增加适合查询和展示的字段：

- `current_stage`：当前阶段稳定键；
- `progress_current`：已完成工作单元数；
- `progress_total`：总工作单元数；
- `started_at`：首次开始执行时间；
- `finished_at`：最终结束时间；
- `heartbeat_at`：最近一次有意义的状态更新；
- `attempt`：任务恢复或重试次数。

现有字段继续保留：

- `scope_type` 与 `scope_id` 标识业务对象；
- `stage` 表示用户要求从哪个业务阶段开始；
- `status` 使用 `pending`、`running`、`succeeded`、`failed`、`cancelled`；
- `parent_run_id` 表示批次与子任务关系；
- `metadata_json` 保存不可变输入快照、模型与提示词锁、阶段清单、阶段结果引用和诊断信息；
- `message`、`error_stage` 保存用户可读状态和失败位置。

进度更新与阶段产物保存必须在同一数据库事务或可重入边界中完成，避免页面看到“阶段成功”却找不到结果。

## 任务类型与阶段

### 逐章拆书

父任务：

```text
scope_type = book_analysis_batch
```

阶段：

1. `prepare_chapters`：锁定确认章节、模型和输入版本；
2. `analyze_chapters`：按一级章节生成拆书稿，最多五章并行；
3. `finalize_book`：汇总章节状态并更新书籍。

每个章节继续使用 `chapter_analysis` 子任务。父任务的进度为已完成章节数 / 总章节数，页面同时显示正在处理的章节名称。章节版本保存成功后立即可查看完整拆书稿。

### 项目知识生成

新增父任务：

```text
scope_type = project_generation
```

阶段：

1. `prepare_analysis`：读取全部成功拆书稿并锁定输入签名；
2. `compress_mind_map_source`：仅在对应输入过长时执行；
3. `compress_album_source`：仅在对应输入过长且不能复用压缩结果时执行；
4. `generate_mind_map`；
5. `generate_album_outline`；
6. `validate_album_outline`；
7. `save_project_outline`。

思维导图和专辑大纲模型调用可以并行，但各自独立保存阶段状态。思维导图写入 `mind_maps` 后立即展示；专辑大纲原始 JSON 继续写入项目草稿字段，结构校验成功后生成声音并进入审核状态。一个分支失败不删除另一分支已经成功的结果。

### 单条声音

继续使用：

```text
scope_type = episode
```

阶段：

1. `episode_outline`；
2. `episode_draft`；
3. `episode_final`。

每个阶段生成成功后立即写入 `artifact_versions` 并更新任务进度。页面可直接查看刚完成的细纲或初稿，不等待终稿。

### 批量声音

继续使用：

```text
scope_type = project_batch
```

父任务进度为已经结束的声音数 / 总声音数；每条声音是子任务并保留自身三个阶段。最多五条声音并行，单条失败不会停止后续声音。

## 创建与执行协议

所有长任务的 POST 接口采用统一行为：

1. 校验用户当前操作是否允许；
2. 解析并锁定业务输入、模型版本和提示词版本；
3. 检查同一对象、同一任务类型是否已有活动任务；
4. 在 SQLite 创建 `pending` 任务；
5. 通过受控的应用任务注册器启动后台协程；
6. 立即返回 HTTP 202 和任务详情。

重复点击默认返回现有活动任务，不创建重复模型调用。任务注册器保存当前进程内的协程引用，确保异常可以写回任务状态，并避免未追踪的 `create_task` 被垃圾回收。

## 阶段检查点与幂等恢复

每个任务在元数据中保存有序阶段清单与检查点：

```json
{
  "stages": {
    "prepare_analysis": {"status": "succeeded"},
    "generate_mind_map": {
      "status": "succeeded",
      "artifact_type": "mind_map",
      "artifact_id": "..."
    },
    "generate_album_outline": {"status": "running"}
  }
}
```

恢复规则：

- `succeeded` 阶段必须验证产物仍存在，然后跳过；
- `pending` 或进程退出时留下的 `running` 阶段重新进入执行；
- `failed` 阶段仅在用户点击重跑或任务恢复策略明确允许时重试；
- `cancelled` 任务不自动恢复；
- 任务使用创建时锁定的模型、提示词和输入签名；
- 保存阶段结果前检查同一任务和阶段是否已有成功产物，避免重复版本。

应用启动时统一扫描所有支持的顶层活动任务：

- `book_analysis_batch`
- `project_generation`
- `episode`
- `project_batch`

遗留的 `running` 状态先标记为可恢复的 `pending`，增加 `attempt` 后交给对应执行器。子任务由父任务统一协调，防止父子同时恢复造成重复调用。

## API 设计

### 创建任务

现有业务入口保留路径，响应改为 HTTP 202：

- `POST /api/books/{book_id}/analyze`
- `POST /api/books/{book_id}/chapters/{chapter_id}/analyze`
- `POST /api/projects/{project_id}/generate-outline`
- `POST /api/episodes/{episode_id}/generate`
- `POST /api/projects/{project_id}/batch`

统一响应至少包含：

```json
{
  "run": {
    "id": "...",
    "scope_type": "project_generation",
    "scope_id": "...",
    "status": "pending",
    "current_stage": "prepare_analysis",
    "progress_current": 0,
    "progress_total": 5
  },
  "reused": false
}
```

### 查询任务

- `GET /api/runs?status=active`：全局活动任务；
- `GET /api/runs?scope_type=...&scope_id=...`：某业务对象的任务；
- `GET /api/runs/{run_id}`：任务详情、阶段和子任务；
- `GET /api/runs/{run_id}/outputs`：可展示的已完成阶段产物摘要与正文。

现有运行记录列表继续提供历史任务。活动任务查询必须避免返回输入快照和完整原文，完整阶段产物只通过受控输出接口按业务权限读取。

## 前端体验

### 全局任务中心

应用根组件始终轮询活动任务，不依赖当前选中的书籍、项目或页面。默认一秒一次；没有活动任务时降至低频或停止，创建任务后立即恢复。

左侧导航增加任务状态摘要：

- 运行中数量；
- 失败数量；
- 最近完成提示。

点击后进入现有“运行记录”页面。

### 工作区进度卡

书籍、项目和声音页面根据 `scope_type + scope_id` 自动匹配任务：

- 状态标题；
- 当前阶段中文名称；
- 数量进度条；
- 已运行时间；
- 当前处理章节或声音；
- 已完成阶段列表；
- 失败信息、重试与取消操作。

按钮不再依赖页面内 `busy` 判断任务是否运行，而是根据后端活动任务禁用并显示“查看进度”。

### 阶段输出

完成一个阶段后，进度卡出现可展开结果：

- 章节拆书稿；
- 思维导图；
- 专辑大纲；
- 声音细纲；
- 声音初稿；
- 声音终稿。

默认展示摘要，展开后读取完整正文。生成中的阶段只显示状态、耗时和模型，不展示虚假的空输出。

### 刷新恢复

页面启动时并行读取书籍、项目和活动任务。选中的书籍、项目与主要视图写入 URL 或 `localStorage`；如果目标对象仍存在则恢复工作区，否则回到对应列表。即使没有恢复具体工作区，全局任务中心仍会显示活动任务。

## 错误、取消与重跑

- 模型、解析、校验和保存错误分别记录稳定错误类别；
- 父任务汇总子任务成功、失败和取消数量；
- 已成功阶段和产物不会因后续失败被删除；
- 用户取消只阻止尚未开始的新阶段，正在执行的非流式模型请求在返回后丢弃结果或按取消标记停止保存；
- 重跑默认从失败阶段继续；
- 若用户修改输入、模型或提示词后希望重新生成，创建新任务并形成新快照，而不是篡改旧任务。

## 兼容与迁移

- `workflow_runs` 新字段通过现有幂等列迁移添加；
- 历史运行缺少进度字段时按状态推断为 0% 或 100%，仍可正常查看；
- 现有声音批次和产物数据无需迁移；
- 启动恢复只处理新任务元数据版本完整的活动任务；
- 对无法安全恢复的遗留活动任务标为失败并给出“请重新运行”，不得猜测旧输入。

## 测试与验收

### 后端

- 每个长任务接口在模型结束前返回 202；
- 同一对象重复点击复用活动任务；
- 阶段进度和输出检查点正确写入；
- 模拟进程退出后，恢复时跳过成功阶段并继续未完成阶段；
- 父子任务恢复不会重复执行；
- 取消、失败隔离、从失败阶段重跑；
- 模型与提示词快照在恢复后保持不变；
- 活动任务接口不泄露完整原文输入。

### 前端

- 任务创建后立即出现进度卡；
- 进度随轮询更新；
- 阶段完成后可查看结果；
- 重新挂载页面后自动恢复活动任务；
- 当前工作区未恢复时，全局任务中心仍能找到任务；
- 任务完成、失败和取消后按钮状态正确。

### 手工回归

使用慢速演示供应商分别启动：

1. 一次多章节拆书；
2. 一次思维导图与专辑大纲生成；
3. 一条声音三阶段生成；
4. 一次多声音批量生成。

在每种任务运行中刷新浏览器，确认任务继续且页面恢复进度；随后在阶段之间重启后端，确认从检查点续跑且不重复生成已有版本。
